CUDA code generation of the YASAKANI compressed GEMM kernels (static analysis, sm_120)
======================================================================================

Nothing in this file was measured on a GPU.  No CUDA or SYCL program was run.  The numbers are of two kinds and
every table says which:
  [SASS]   counted in the SASS listing (cuobjdump -sass) with scripts/sass_count.py
  [SRC]    derived by reading the upstream source (paths relative to the upstream tree, e.g. src/lnord.cu:290)
  [GIVEN]  B60 numbers quoted from the task description, not re-counted here

How it was produced
-------------------
  scripts/cuda_codegen.sh <upstream tree> results/cuda_codegen        (NVCC=nvcc, CUOBJDUMP=cuobjdump from the environment)
      nvcc release 13.1 (V13.1.115), -arch=sm_120 -O3 --fmad=false -std=c++17 -DYSKN_KVX_MODE=3 -I src -I include
      units: gemm_compressed.cu lnord.cu pfa.cu q35_g6.cu  ->  .o, .ptx, .sass, .elf.txt
  scripts/sass_count.py <unit>.sass --elf <unit>.elf.txt -f <regex of the mangled name> [--weight ...] [--range ...]
  The complete output of cuda_codegen.sh is 76 MB, so results/cuda_codegen/ keeps only
      <unit>.analysed.sass   SASS of the functions analysed here (sass_count.py --extract)
      <unit>.analysed.ptx    PTX of the same entry points
      <unit>.nvinfo.txt      the "function: ... register count / frame size / min stack size" lines of cuobjdump -elf
      BUILD_INFO.txt
  sass_count.py reads these reduced files exactly like the full ones; the commands are repeated in section 6.

2. What one loop trip decodes (trip -> weights mapping)                                                  [SRC]
----------------------------------------------------------------------------------------------------------------
Common decode (lnord.cu:265-266, 286-295; pfa.cu:172-173, 205-209; q35_g6.cu:54-62):
  * one trip handles one "half" = 256 columns of one 16-row tile.  Lane (gi = lane >> 2, tig = lane & 3) owns rows gi and
    gi + 8 and the 64-column chunk tig.  Per trip it holds 2 * K words of code (K/2 uint4 loads, lnord.cu:271).
  * per m-step (8 per trip, unrolled) a lane extracts 2 fields of 4K bits (lno_field), splits each into 2 pairs of steps and
    calls pair_a 4 times; each pair_a does 2 table lookups (uint16 = 2 int8 weights) -> one 32-bit register = 4 weights.
    So per m-step: 8 lookups and 16 weights per lane = 256 lookups and 512 weights per warp
    (16 rows x 32 columns: exactly the 16x32 "A" operand of one m16n8k32 MMA).
  * per trip: 8 m-steps -> 64 lookups per lane, 2048 lookups and 4096 weights (16 rows x 256 columns) per warp.
    This is the same unit as one B60 trip (4096 weights, 2048 table lookups).

  kernel                 loop in the source                   weights decoded per warp-trip   input rows (tokens) per trip   MMA per lane-trip
  LNORD MT = 8           for bi (lnord.cu:267-319)            4096 (16 rows x 256 cols)        8                              8   (1 per m-step)
  LNORD MT = 16          same, NB = 2                         4096                             16                             16
  PFA NF = 4             for bi (pfa.cu:174-292), SS = 8,     4096                             64                             64  (2 per m-step per 16 tokens;
                           NST = 1 (pfa.cu:89: NF > 4 ? 4 : 8)                                                                      here the weights are operand B, 2 x 8 rows)
  gemm_kernel            for hi (gemm_compressed.cu:55-90)    4096 (2 x 8 rows x 256 cols)     32                             32
  G6 predecode           straight line (q35_g6.cu:47-68)      4096 per warp, once              -                              0
  G6 GEMM MB = 4         for u (q35_g6.cu:183-275): 8 stages  16384 CONSUMED per warp          64 per warp (128 per CTA)      256
                           of 64 columns                        (32 rows x 512 cols, no decode)
  G6 GEMM MB = 2         same                                 16384 consumed per warp          32 per warp (64 per CTA)       128

  One MMA instruction (m16n8k32) is one warp-wide operation = 16 x 8 x 32 = 4096 int8 multiply-accumulates.
  In every kernel above  (MMA per trip) x 4096 = (weights per trip) x (tokens per trip): no MMA capacity is wasted
  when all token slots are used.  With fewer rows than the capacity (M = 1 in the MT = 8 kernel) the unused slots multiply zeros.

  The XSUM accumulation (acc64 += A * sum) runs once per 512 columns = every second trip (blk == 1; lnord.cu:303-318,
  pfa.cu:226-242); in G6 once per u (q35_g6.cu:210-225).  In the "weighted" columns below the basic block that holds it
  has weight 0.5 where the compiler kept it as a separate, branch-guarded block.

3. Normalisation
----------------------------------------------------------------------------------------------------------------
A SASS listing is the program of ONE thread; each listed instruction is executed by the 32 threads of a warp, i.e. it is a
32-lane instruction ("warp-instruction").  The MMA is listed once and is one warp-wide tensor-core operation.
A B60 ESIMD instruction operates on 16 lanes.  Two normalisations are given:
  (a) instructions per 512 decoded weights:  CUDA = listed instructions per trip / 8;  B60 = ESIMD instructions per trip / 8
      (both generators decode 4096 weights per trip; for the G6 GEMM, which decodes nothing, per 512 weights consumed = / 32)
  (b) lane-operations per weight:            CUDA = listed instructions x 32 / 4096;   B60 = ESIMD instructions x 16 / 4096
"weighted" = static count with the every-second-trip accumulate block at weight 0.5 (and, for G6, the pointer set-up
block psetup, q35_g6.cu:111-120, at weight 1 / (8 G)); predicated instructions count as 1.  Loops nested inside the
trip (the cp.async staging loops of PFA and gemm_kernel) are counted once although they run 2..4 times per trip.

4. Details extracted from SASS / PTX
----------------------------------------------------------------------------------------------------------------
4.1 The 64-bit product  acc64 += A * (long long)sum                                                      [SASS + PTX]
  source   lnord.cu:309-311:  A0 = (long long)__float2int_rn(__fmul_rn(a0, rm));  acc64 += A0 * (long long)d;
  PTX      mul.rn.f32 %r1297, %r1461, %r1413 ;  cvt.rni.s32.f32 %r1298, %r1297 ;
           mul.wide.s32 %rd236, %r1298, %r1431 ;  add.s64 %rd288, %rd236, %rd288
           (the front end already narrowed the s64 x s64 product to a widening 32 x 32 multiply)
  SASS     FMUL R30, R30, R53 ;  F2I.NTZ R37, R30 ;  IMAD.WIDE R70, R44, R37, R70
           i.e. ONE instruction: signed 32 x 32 -> 64 multiply plus 64-bit accumulate into the register pair R70:R71.
           No IADD.64, no carry chain, no 64 x 64 multiply.  F2I.NTZ is what cvt.rni (round to nearest even) becomes.
  PFA and G6 write it by hand as inline PTX "mad.wide.s32" (pfa.cu:79, q35_g6.cu:34) -> the same IMAD.WIDE.
  gemm_kernel<K,true>: same PTX (mul.wide.s32 + add.s64) and same SASS (16 FMUL + 16 F2I.NTZ + 16 IMAD.WIDE per trip).
  The accumulator zeroing after the product is CS2R Rn, SRZ (clears two registers).

4.2 Float multiply + add stay unfused                                                                    [SASS + PTX]
  PTX of all four units: 0 occurrences of "fma".  Non-XSUM kernels (lno_madd / madd_rn = __fadd_rn(acc, __fmul_rn(a, b))):
  PTX cvt.rn.f32.s32 ; mul.rn.f32 ; add.rn.f32  ->  SASS I2FP.F32.S32 ; FMUL ; FADD (gemm_kernel<6,false>: 16 + 16 + 16 per
  trip, lnord_kernel<6,8,false,...>: 4 + 4 + 4, no FFMA in either loop).
  FFMA does appear in the SASS, but only in code the compiler generates for div.rn.f32 (__fdiv_rn: MUFU.RCP followed by FFMA
  correction steps, plus the subroutine $__internal_N_$__cuda_sm3x_div_rn_noftz_f32_slowpath) and for rsqrtf/ldexpf in
  the prologues.  None of it is in an XSUM hot loop; the XSUM loops contain only FMUL and F2I.

4.4 The MMA                                                                                              [SASS]
  PTX mma.sync.aligned.m16n8k32.row.col.s32.s8.s8.s32  ->  SASS  IMMA.16832.S8.S8 R44, R24.ROW, R40.COL, R44

5. Algorithmic structure of the CUDA GEMM paths (for a port)                                             [SRC]
----------------------------------------------------------------------------------------------------------------
5.1 Data layout shared by all paths
  * Code stream "lno" (built once at load by lnord_build, lnord.cu:58-88, engine35.cpp:162; pure permutation, same size as
    the file stream, N*Kc*K/16 bytes, lnord.cu:79): index [tile16][g][blk][u][lane] of uint4, u = 0..K/2-1.  A lane's
    K/2 uint4 = 2K words = chunk tig (64 columns) of rows gi and gi+8 of a 16-row tile, for one half blk (256 columns) of
    one 512-column group g.  One warp-wide 16-byte load per u is fully coalesced (32 x 16 bytes contiguous, lnord.cu:191).
  * Table: 4096 x uint16 (two int8 weights per 12-bit state), copied by every CTA into shared memory at kernel start
    with 512 uint4 loads: __shared__ uint16_t s_lut[4096] = 8 KB, REP = 1 (lnord.cu:181, 209; pfa.cu:91, 151; q35_g6.cu:38-40).
    Only the old gemm_kernel uses REP = 2 (every entry stored twice, 16 KB, index s*2 + (g & 1) to spread lanes over
    bank pairs; v2_decode.cuh:27, 33-43; gemm_compressed.cu:6, 24, 71).
  * State extraction: fields of 4K bits (2 pairs of steps) are cut from the 2K words with shift/or (lno_field,
    lnord.cu:39-44); the 12 - K carry bits of the previous 64-column chunk come from the neighbouring lane with one
    __shfl_sync per trip (lnord.cu:286-288), then chain inside the lane (q0 = p20 >> TS, lnord.cu:295).

5.2 LNORD (M <= 16; the decode path)   src/lnord.cu:173-376
  * One warp = one 16-row tile; a CTA = UW warps (2 for M = 1,3; 4 for M = 2,4..8 and for M = 9..16; lnord.cu:29, 421-425).
  * Worker split over columns: grid = (ctas, max_workers) (lnord.cu:401); worker = blockIdx.y takes the column groups
    g = worker + k * nw, k = 0..ng-1 (round robin, lnord.cu:190, 192, 268) and loops nblk = 2 * ng trips of 256 columns.
    n_workers per tensor: table {down 9, gate 5, up 5, q/k/v/o/out 4, qkv/z 8} (engine35.cpp:122); for M >= 4 it is
    replaced by nw_big = max(1, min(G, ceil(8 * SM_count / (N/64)))) (engine35.cpp:139-142, 407).
    gate/up: G = 10, nw = 5 -> each warp runs 4 trips; down: G = 34, nw = 9 -> 6 or 8 trips.
  * Each trip: 8 m-steps; per m-step 8 lookups per lane -> the 16x32 weight operand A[4]; one MMA per group of 8 rows
    (NB = 1 for MT = 8, 2 for MT = 16) with the input fragment as operand B (lnord.cu:290-302).
  * Input rows are NOT staged in shared memory: each lane loads one uint4 (16 bytes of qx) from global memory per two
    m-steps per row group, directly (lnord.cu:298).  For M <= 8 the engine writes qx in the interleaved "LO" layout
    (8 rows x 512 columns in 4096 bytes, 16-byte pieces of the 8 rows adjacent; lnord.cu:284, A_gemv.md section 3.4) so
    that these loads of a warp are contiguous.
  * Prefetch pipeline: the codes of trip bi+1 are loaded (__ldg) at the top of trip bi into nx[] (lnord.cu:271-274);
    optional second look-ahead LOOK = 2 and extra touches (YSKN_LNO_LOOK / PREW) are off by default.  With programmatic
    dependent launch (pdl.cuh:12-13) the table copy and the first code load are issued BEFORE griddepcontrol.wait, i.e.
    while the previous kernel still runs (P.pre = 3, lnord.cu:210-214).
  * Every second trip (blk == 1, end of a 512-column group): A = rint(alpha[tok][g] * rm[tok]) and
    acc64[4] += A * d[4]; d = 0 (lnord.cu:303-318).  rm = 2^24 / max_g alpha is computed in the prologue with warp
    shuffles (lnord.cu:236-264), us_out is written by CTA (0,0).
  * Output: 4 atomicAdd(uint64) per lane per row group into part[tok][N] (lnord.cu:353-354), because the workers of one
    row tile are different CTAs.  The sum is exact, so the order is irrelevant.
  * Launches: ONE kernel launch per gemv call for up to 3 matrices that share the input (segments, e.g. gate+up, q+k+v;
    lnord.cu:182-183, 398-408; engine35.cpp:404-408).  gate+up with M = 2,4..8: grid 544 x 5 CTAs of 128 threads;
    M = 1,3: 1088 x 5 CTAs of 64 threads.

5.3 PFA (17 <= M <= 255)   src/pfa.cu:85-321, launch 332-365
  * grid = (ceil(M/64), row-tile CTAs, 1): blockIdx.x = tile of 64 tokens (NF = 4 fragments of 16), blockIdx.y = WPC warps,
    each warp = one 16-row weight tile.  No worker split (FOLD = 1): a warp walks all G groups, nblk = 2G trips
    (pfa.cu:105, 181), keeps its int64 accumulators in registers and writes float y = acc * us [* rr] itself at the end
    (pfa.cu:301-310) - no atomics, output buffer is float [tok][N].
  * WPC (warps per CTA) is chosen at launch: ceil(tasks / (2 * SM_count)) clamped to 1..6 (pfa.cu:348-353, 358).
